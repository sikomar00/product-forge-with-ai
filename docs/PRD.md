# Product Forge With AI — PRD v1.1

2026-11-09 · v1.1 승인(v1.0에 ERD 단계의 M0-03·M0-04 수정과 M0-19 추가를 반영).

## 문서 개요

- 이 문서는 게임(엔진과 콘텐츠)의 요구사항을 제작 단계별 ID로 정리한다. 배경, 커리큘럼(18장·미션 207개), 비용, 연구 근거는 `docs/design.md`를 기준으로 하고 여기서 반복하지 않는다(2026-11-09 결정).
- 범위: M0·M1은 상세히 쓰고, M2~M4는 목표와 범위만 둔다. 각 단계를 시작하기 전에 상세화한다(2026-11-09 결정). 1·2장 실측 전이라 뒤 단계 수치는 바뀔 가능성이 크기 때문이다.
- 함께 보는 문서: `docs/GLOSSARY.md`, ADR-0001~0009, `docs/IA.md` v1.1, `docs/USER-JOURNEY.md` v1.0.
- OpsDesk 자체의 요구사항은 이 PRD의 범위 밖이다. 학습자가 3장에서 OpsDesk의 PRD를 직접 쓴다.

## 비전과 원칙

비전: 학습자가 AI와 함께 OpsDesk를 기획부터 운영·개선까지 만들면서, 단계마다 어떤 도구의 어떤 기능을 왜 쓰는지 설명하고, 고르고, 검증하고, 진단할 수 있게 된다(design.md 0절, 2.1절의 네 가지 능력).

1. **실제 도구, 실제 상태로 채점한다.** 화면 출력이 아니라 시스템 상태를 읽기 전용으로 검사한다(ADR-0004).
2. **정답은 학습자 눈에 띄지 않는다.** 콘텐츠는 별도 비공개 리포에 두고, 보고에는 미션 ID·개수·테스트 결과만 쓴다(ADR-0006, ADR-0009).
3. **장애 주입은 안전 원칙 안에서만 한다**(ADR-0007).
4. **콘텐츠는 학습자보다 한 장 앞서서만 만들고, 코어를 먼저 만든다**(design.md 9절).
5. **측정하고 고친다.** 텔레메트리로 예상과 실측을 비교하고, 1·2장을 마치면 일정을 다시 계산한다(design.md 3.8절).

## 문제 정의, 대상 사용자, 비목표

- **문제**: 바이브코딩으로 결과물을 만들 수는 있어도, 각 단계의 도구가 무엇이고 왜 쓰는지 모르면 AI가 만든 결과를 검증하지 못한다. 근거는 design.md 1.3절(AI 도움을 받은 집단의 퀴즈 점수가 더 낮았던 RCT 등)이다.
- **대상 사용자**: 1명. 부트캠프에서 바이브코딩을 배우는 학습자이면서, 엔진을 AI와 바이브코딩하는 엔진 개발자다(UJ). Mac Apple Silicon, 주 20시간 이상.
- **비목표**: 여러 사용자와 리더보드, LLM 서술형 채점(design.md 부록 A.4), 웹 화면(명령형 CLI로 정함, IA), Windows 지원.

**완료 기준 (게이트)**

- S1 미션 52개의 모범 답안이 새 엔진에서 모두 통과하고, 같은 시나리오의 보상(XP)이 S1과 같다.
- 가짜 미션으로 IA-1~IA-11, IA-15~IA-17이 모두 동작한다(명령마다 테스트).
- 엔진 리포에 콘텐츠 파일이 없다.
- `quest status --json` 출력에 체크 설명·힌트·정답이 없다(테스트).
- 500줄을 넘는 파일이 없다(`rules/code.md`).
- 엔진이 만드는 스키마가 `docs/ddl/v1.0.sql`과 같고, 점검 67개(`docs/ddl/v1.0-checks.sql`)를 통과한다.

**범위 밖**: 체크 프리미티브(M1부터), 장애 주입 실행, 실제 콘텐츠, 랩.

### M1 · 0~4장

목표: 0~4장(미션 57개, 코어 50개)을 처음부터 끝까지 플레이할 수 있다. 0장 부분(0장 콘텐츠, `quest doctor`, `quest update`)은 0장 시작 전에, 1~4장은 학습자보다 한 장 앞서서 만든다(CLAUDE.md 불변 규칙). 사람이 미리 플레이하면 그 장의 학습 효과가 사라지므로, 검수는 자동 플레이스루로 한다(2026-11-09 결정).

| --- | --- | --- |

| M1-06 | 1장용 Linux VM 랩을 게임이 만들고 라벨을 붙인다. VM 도구는 Spec·Plan에서 정한다. | design.md 1장 |
| M1-07 | 2장용 리뷰봇 워크플로를 만든다. 리뷰봇이 지적할 항목 목록은 콘텐츠 리포에 둔다. | design.md 2장, ADR-0009 |
| M1-08 | 0~4장 코어 미션 50개가 design.md 8.7절 완성 기준을 충족한다. 체크마다 풀린·안 풀린·흔한 실수 상태 테스트가 있고, 힌트 규칙, 카드, `est_min`이 있다. | design.md 8.7절 |

| M1-10 | 콘텐츠 작업 보고는 스포일러 규칙을 따른다(미션 ID, 개수, 테스트 결과만). | CLAUDE.md 6절 |

**완료 기준 (게이트)**

- 0~4장 코어 미션 50개의 미션 테스트가 모두 통과한다.
- 자동 플레이스루가 0장 첫 미션부터 4장 보스까지 모두 통과한다.
- 체크 프리미티브 6종의 단위 테스트와 읽기 전용 테스트(NF-02)가 통과한다.
- 장애 미션 2개(1-I1, 2-I1)의 inject·verify·cleanup·abort 테스트가 통과한다.
- `quest update`와 `quest selftest`가 시험용 콘텐츠 리포로 동작한다.

**범위 밖**: 5장 이후 콘텐츠, M2 이후 체크, ➕선택 미션 7개(학습자가 열 때 만든다).

### M2 · 5~9장 (개요)

목표: 백엔드·비동기·프론트엔드·테스트·컨테이너 장을 플레이할 수 있다. 체크는 db·authz·api_contract·mail·node·e2e·tools·docker다. docker 체크는 9장(컨테이너)에 필요하므로 설계서 9절과 달리 M2에서 만든다(이 PRD에서 바로잡음). 요구사항과 게이트는 M2를 시작하기 전에 상세화한다.

### M3 · 10~14장 (개요)

목표: 배포·CI/CD·쿠버네티스 비교·클라우드·IaC·운영 장을 플레이할 수 있다. 체크는 saas·terraform·k8s다. 요구사항과 게이트는 M3를 시작하기 전에 상세화한다.

### M4 · 15~17장 (개요)

목표: 제품 안의 AI, 분석·개선, Forge Run 장을 플레이할 수 있다. ai_eval 체크, 합성 트래픽 시뮬레이터, 온콜 주간(IA-14), `quest stats` 확장을 만든다. 요구사항과 게이트는 M4를 시작하기 전에 상세화한다.
